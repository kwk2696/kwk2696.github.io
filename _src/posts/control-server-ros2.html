[Robosynapse] Control Server: Running ROS2 on Docker

2026-09-19
robosynapseros2 {{SWITCH}}

로봇 매니퓰레이션 시스템을 만들 때 가장 먼저 필요한 것은 로봇 팔에 명령을 보내고 상태를 받아오는 Control Server입니다. 이 글은 제가 진행 중인 robosynapse 프로젝트에서 UR7e와 AgileX Piper 두 종류의 로봇 팔을 위한 Control Server를 구축한 과정을 정리한 것입니다. ROS2 환경을 Docker로 올리는 것부터 로봇과의 네트워크 연결, 드라이버와 MoveIt 실행까지 순서대로 다룹니다.

전체 구조는 단순합니다. Control Server는 ROS2 Humble 컨테이너 안에서 로봇 드라이버와 MoveIt을 돌리고, 상위의 Inference Server(VLA 모델이 도는 곳)가 보내는 명령을 로봇에 전달합니다. 두 서버는 한 머신에 있을 수도, 분리되어 있을 수도 있습니다.

The first thing a robot manipulation system needs is a control server: the machine that sends commands to the arm and reads its state back. This post walks through how I set one up for two different arms, a UR7e and an AgileX Piper, as part of my ongoing robosynapse project. It covers running ROS2 in Docker, wiring up the network to the robot, and launching the drivers and MoveIt, in that order.

The overall shape is simple. The control server runs the robot driver and MoveIt inside a ROS2 Humble container, and passes commands down to the robot from the inference server above it, where the VLA model runs. The two servers may share one machine or sit on separate ones.

두 서버를 굳이 나누는 이유는 요구사항이 정반대이기 때문입니다. Control Server는 로봇 옆에 물리적으로 붙어 있어야 합니다. 컨트롤박스와 같은 스위치에 물리는 이더넷, USB-CAN 어댑터처럼 선으로 연결되는 장치들이 전부 여기에 달리기 때문입니다. 반면 Inference Server는 VLA 모델을 올릴 GPU만 있으면 되고 로봇과 같은 공간에 있을 이유가 없습니다. 연구실 공용 GPU 서버일 수도, 클라우드 인스턴스일 수도 있습니다.

0. 왜 Docker 위에 ROS2인가

ROS2는 배포판(Humble, Iron, ...)마다 Ubuntu 버전 의존성이 강하고, 호스트에 직접 설치하면 환경이 쉽게 오염됩니다. osrf/ros:humble-desktop-full 이미지를 쓰면 어떤 호스트에서든 동일한 환경을 재현할 수 있고, 로봇마다 컨테이너를 분리해 ROS_DOMAIN_ID로 격리하는 것도 간단해집니다. 여러 대의 로봇을 한 서버에서 다룰 때 이 구조의 이점이 더 커집니다.

1. UR7e Control Server

1-1. ROS2 Humble 컨테이너 띄우기

RViz 같은 GUI를 컨테이너 안에서 쓰기 위해 X11 소켓을 공유하고, DDS 통신을 위해 --net=host로 띄웁니다.

The reason to split the two servers is that their requirements pull in opposite directions. The control server has to sit physically next to the robot: everything that connects by cable hangs off it, from the ethernet link into the control box to the USB-CAN adapter. The inference server, on the other hand, only needs a GPU big enough for the VLA model and has no reason to be in the same room. It can just as well be a shared lab GPU box or a cloud instance.

0. Why ROS2 on Docker

Each ROS2 distribution (Humble, Iron, and so on) is tightly bound to a particular Ubuntu release, and installing it straight onto the host tends to pollute the machine. Using the osrf/ros:humble-desktop-full image reproduces the same environment on any host, and it also makes it easy to give each robot its own container isolated by ROS_DOMAIN_ID. That advantage grows once you drive several robots from one server.

1. UR7e control server

1-1. Starting the ROS2 Humble container

Share the X11 socket so GUI tools like RViz work inside the container, and start it with --net=host for DDS communication. 

ROS2 Docker Entryxhost +local:root

docker run -it \
    --name ros2_humble \
    --privileged \
    --net=host \
    --ipc=host \
    --gpus all \
    -e DISPLAY=$DISPLAY \
    -v /tmp/.X11-unix:/tmp/.X11-unix:rw \
    -v ~/ros2_ws:/root/ros2_ws \
    --device /dev/video0:/dev/video0 \
    --device /dev/input:/dev/input \
    osrf/ros:humble-desktop-full


# 이후 재사용


# reusing it later

docker start ros2_humble
docker exec -it ros2_humble /ros_entrypoint.sh bash

1-2. UR 드라이버 설치

UR 시리즈는 ROS 공식 배포판(rosdistro)에 릴리즈되어 있어서 apt 바이너리 설치 한 줄이면 끝납니다.

1-2. Installing the UR driver

The UR series is released into the official ROS distribution (rosdistro), so a single apt install is all it takes. 

ROS2 UR Package Installsudo apt update
sudo apt install -y ros-humble-ur

sudo apt install -y ros-humble-ros2controlcli   # force control 용
sudo apt install -y ros-humble-ros2controlcli # for force control

주의할 점: 이 패키지들은 컨테이너 내부 파일시스템(/opt/ros/humble/...)에 설치되므로 컨테이너를 rm하면 사라집니다. 자주 다시 만든다면 Dockerfile에 넣거나 commit해 두는 것이 좋습니다.

1-3. 로봇과의 내부망 설정

Control Server와 로봇은 같은 스위치에 물려 있어야 하고, 로봇 컨트롤박스와 같은 대역의 고정 IP를 서버 쪽 이더넷 인터페이스에 부여합니다.

One caveat: these packages land in the container's own filesystem under /opt/ros/humble/..., so they disappear the moment you rm the container. If you rebuild often, bake them into a Dockerfile or commit the image.

1-3. Setting up the robot network

The control server and the robot have to share a switch, and the server's ethernet interface needs a static IP in the same range as the robot control box. 

Robot networksudo ip addr add 172.16.0.10/24 dev enp1s0

ip -br addr   # 확인
ip -br addr # check

위 방식은 재부팅하면 사라지므로, netplan으로 고정해 둡니다.

That assignment is lost on reboot, so pin it down with netplan. 

/etc/netplan/01-robot.yamlnetwork:
  version: 2
  ethernets:
    enp1s0:
      addresses: [172.16.0.10/24]
sudo netplan apply

1-4. UR Driver & MoveIt 실행

1-4. Launching the UR driver and MoveIt

UR Driver Init & MoveItsource /robo-synapse/config/setup_env.sh

ros2 launch ur_robot_driver ur_control.launch.py \
    ur_type:=ur7e robot_ip:=172.16.0.3 launch_rviz:=false

ros2 launch ur_moveit_config ur_moveit.launch.py \
    ur_type:=ur7e

두 launch를 모두 띄운 뒤, 마지막으로 티치 펜던트에서 실행 버튼을 눌러야 외부 제어(External Control)가 시작됩니다. 이걸 잊으면 드라이버는 떠 있는데 로봇이 움직이지 않는 상태가 됩니다. robosynapse에서는 Control/Inference Server가 분리된 환경과 아닌 환경을 자동으로 감지하는 스크립트(run_ur_driver.sh, run_ur_moveit.sh)로 이 과정을 감싸 두었습니다.

2. Piper Control Server

AgileX Piper는 UR과 결이 다릅니다. 가장 큰 차이 두 가지:

  • 패키지가 rosdistro에 릴리즈되어 있지 않습니다. ros-humble-piper 같은 apt 바이너리가 없고, AgileX가 GitHub에 올려둔 piper_ros를 직접 clone해서 colcon으로 빌드해야 합니다.
  • 통신이 이더넷이 아니라 CAN입니다. USB-CAN 어댑터를 통해 CAN 인터페이스를 활성화하는 단계가 추가됩니다.

2-1. 컨테이너 띄우기

UR과 동일한 ros:humble 이미지에서 시작하되, CAN 장치 접근을 위해 /dev와 udev를 통째로 마운트합니다.

Once both launches are up, you still have to press the play button on the teach pendant before External Control actually starts. Forget it and you end up with a driver that is running while the robot refuses to move. In robosynapse I wrap all of this in scripts (run_ur_driver.sh, run_ur_moveit.sh) that detect whether the control and inference servers are split across machines.

2. Piper control server

The AgileX Piper works differently from the UR in two important ways.

  • The package is not released into rosdistro. There is no apt binary like ros-humble-piper; you clone AgileX's piper_ros from GitHub and build it with colcon yourself.
  • It talks over CAN rather than ethernet, which adds a step for bringing up the CAN interface through a USB-CAN adapter.

2-1. Starting the container

Start from the same ros:humble image as the UR, but mount /dev and udev wholesale so the CAN device is reachable. 

Piper Docker Entrydocker run -it \
  --name ros2_humble \
  --privileged \
  --net=host \
  --ipc=host \
  -e DISPLAY=:0 \
  -v /tmp/.X11-unix:/tmp/.X11-unix:rw \
  -v /dev:/dev \
  -v /run/udev:/run/udev:ro \
  -v $HOME/workspace:/root/workspace \
  osrf/ros:humble-desktop-full

bin/control_server/create_docker.sh piper   # 컨테이너 ros2_humble_piper, domain=42
# in robosynapse this is a single script: bin/control_server/create_docker.sh piper # container ros2_humble_piper, domain=42

Piper ships scripts that find the CAN port and bring it up at 1 Mbps. I use can_piper0 as the default interface name.

ip -br link show can_piper0   # UP 확인

3. Bimanual Piper: 컨테이너로 팔 분리하기

Piper 두 대를 양팔로 쓰는 bimanual 구성은 현재 개발 중입니다. 정리가 끝나는 대로 이 섹션에 추가할 예정입니다.

정리

  • ROS2는 호스트에 직접 깔지 말고 osrf/ros:humble-desktop-full 컨테이너로. DDS 때문에 --net=host는 사실상 필수.
  • UR처럼 rosdistro에 릴리즈된 로봇은 apt 한 줄, Piper처럼 미릴리즈 패키지는 clone + colcon build.
  • 이더넷 로봇(UR)은 netplan으로 고정 IP를, CAN 로봇(Piper)은 can_activate + candump로 링크를 먼저 검증.

Takeaways

  • Don't install ROS2 on the host; use the osrf/ros:humble-desktop-full container. Because of DDS, --net=host is effectively mandatory.
  • Robots released into rosdistro, like the UR, are one apt line. Unreleased packages like Piper mean clone plus colcon build.
  • For ethernet robots (UR), pin the static IP with netplan; for CAN robots (Piper), verify the link first with can_activate and candump.
